مستقلة. لا SQL شُغّل، ولا تعديل على مستودع الخلفية. النص أدناه مسودة يكتب فريق الخلفية هجرته منها، برقم هجرة جديد، ولا تُعدَّل
أي هجرة قائمة.

## التصميم المقترح

```sql
-- مسودة للمراجعة، لا تُشغَّل كما هي. رقم الهجرة يحدده فريق الخلفية.
CREATE TABLE ambs_txn.expense_payments (
  tenant_id                 uuid          NOT NULL,
  id                        uuid          NOT NULL DEFAULT gen_random_uuid(),
  expense_id                uuid          NOT NULL,
  amount                    numeric(18,4) NOT NULL CHECK (amount > 0),
  currency_code             char(3)       NOT NULL REFERENCES currencies(currency_code),
  paid_on                   date          NOT NULL,
  recorded_by_membership_id uuid          NOT NULL,
  idempotency_key           text          NOT NULL,
  created_at                timestamptz   NOT NULL DEFAULT statement_timestamp(),
  PRIMARY KEY (tenant_id, id),
  FOREIGN KEY (tenant_id, expense_id) REFERENCES ambs_txn.expenses(tenant_id, id),
  FOREIGN KEY (tenant_id, recorded_by_membership_id) REFERENCES tenant_memberships(tenant_id, id),
  UNIQUE (tenant_id, recorded_by_membership_id, idempotency_key)
);
ALTER TABLE ambs_txn.expense_payments ENABLE ROW LEVEL SECURITY;
ALTER TABLE ambs_txn.expense_payments FORCE ROW LEVEL SECURITY;
-- لا UPDATE ولا DELETE لأي دور تشغيلي: الدفعة لا تُعدَّل ولا تُحذف؛ عكسها إجراء لاحق مستقل
```

**قواعد تُفرض في دالة الكتابة الواحدة (لا في الواجهة):**

1. `SELECT … FROM ambs_txn.expenses WHERE … FOR UPDATE` على صف المصروف أولًا، فلا تتسابق دفعتان على المتبقي نفسه.
2. المصروف `approved`، وإلا `invalid_transition`.
3. عملة الدفعة = عملة المصروف، وإلا `currency_mismatch`. وعدد منازل المبلغ لا يتجاوز `currencies.decimals`، ولا تقريب.
4. مجموع الدفعات بعد الإضافة ≤ `amount + coalesce(tax_amount, 0)`، وإلا `overpayment`. كل ذلك داخل المعاملة نفسها.
5. تحديث `paid_amount` و`paid_on` و`settlement_status` على صف المصروف في المعاملة نفسها (انظر الخيار أ أدناه).
6. سطر تدقيق لكل دفعة.

**الإجمالي والمتبقي (O-15):** يُحسبان في الخادم من الصف والدفعات، ولا يُخزَّنان عمودين مستقلين. بذلك لا يوجد رقمان قد يختلفان.

## التزامن، وإعادة الإرسال، ووضع القراءة فقط (مراجعة الجولة 11)

المطلوب ثلاثة ضمانات: **لا يتجاوز المدفوع الإجمالي أبدًا**، و**لا تُسجَّل دفعة مرتين**، و**لا تُسجَّل دفعة والاشتراك للقراءة
فقط**. المثال: مصروف معتمد إجماليه `1050.00 AED`، مدفوع منه `400.25`، فالمتبقي `649.75`.

### 1. المحاسب والمالك يسجّلان دفعتين في اللحظة نفسها

كلاهما يرى المتبقي `649.75`، فيرسل المحاسب `649.75` ويرسل المالك `500.00`. لكل منهما `Idempotency-Key` مختلف، لأنهما فعلان مختلفان
من مستخدمين مختلفين.

| الزمن | معاملة المحاسب                                                                                                                 | معاملة المالك                                                                                                                                           |
| :---- | :----------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------ |
| t1    | `BEGIN`؛ يكتب سطر سجل العمليات بحالة `started`؛ `SELECT … FROM expenses WHERE id = E FOR UPDATE` ← يأخذ قفل الصف               | `BEGIN`؛ يكتب سطر سجله `started`                                                                                                                        |
| t2    | يجمع الدفعات: `400.25`؛ `400.25 + 649.75 = 1050.00 ≤ 1050.00` ← مسموح                                                          | `SELECT … FOR UPDATE` على الصف نفسه ← **ينتظر** قفل المحاسب                                                                                             |
| t3    | `INSERT` الدفعة؛ يحدّث `paid_amount = 1050.00`، `settlement_status = paid`؛ يحفظ النتيجة في سجل العمليات؛ `COMMIT` ← يُحرَّر القفل | (ما زال ينتظر)                                                                                                                                          |
| t4    | —                                                                                                                              | يأخذ القفل، ويقرأ الصف **بعد** التزام المحاسب: المدفوع `1050.00`؛ `1050.00 + 500.00 > 1050.00` ← `409 overpayment`؛ `ROLLBACK`. سجله يحفظ النتيجة `409` |

**النتيجة:** دفعة واحدة، والمتبقي `0.00`، والمالك يرى رسالة «الدفعات تتجاوز الإجمالي» ويعيد قراءة المصروف.

**لماذا لا يكفي غير ذلك:**

- **حساب المجموع بلا `FOR UPDATE`:** في `READ COMMITTED` يقرأ الاثنان `400.25` معًا، ويُدرجان معًا، فيصبح المدفوع `1550.00`.
- **قيد `CHECK` على صف المصروف:** يلتقط الحالة فقط إن حُدّث `paid_amount` في المعاملة نفسها. لذلك هو حاجز ثانٍ في الخيار أ، لا
  بديل عن القفل.
- **البديل عن القفل:** `SERIALIZABLE` مع إعادة المحاولة. أوصي بالقفل الصريح لأنه أبسط وأوضح في السجل.

### 2. إعادة إرسال الدفعة بعد انقطاع الاتصال

المحاسب يرسل `649.75` بالمفتاح `K1`، فينقطع الاتصال بعد الإرسال. لا يعرف المتصفح هل التزمت المعاملة أم لا (العقد §4.8: الانقطاع
بعد الإرسال لا يُعامل فشلًا). فيعيد **الطلب نفسه بالمفتاح نفسه `K1`**، وبالجسم نفسه وجيل السياق نفسه.

| ما حدث للطلب الأول         | ما يعيده الخادم للإعادة بـ`K1`                                                          | عدد الدفعات      |
| :------------------------- | :-------------------------------------------------------------------------------------- | :--------------- |
| التزم وضاع الرد            | النتيجة المحفوظة في سجل العمليات (`200` والمصروف كما كان بعد الدفعة)، **دون تنفيذ ثانٍ** | 1                |
| ما زال قيد التنفيذ         | `409 operation_in_progress`؛ لا تنفيذ ثانٍ                                               | 1 أو 0 حسب الأول |
| لم يُحسم ضمن المهلة         | `503 operation_outcome_unknown`؛ الإعادة بالمفتاح نفسه فقط                              | 1 أو 0           |
| تراجع (خطأ قبل الالتزام)   | السجل يحفظ رمز الفشل، فيعيد الرمز نفسه، ولا يُنفَّذ شيء                                    | 0                |
| `K1` بجسم مختلف (مبلغ آخر) | `422 idempotency_key_reused`، ولا تنفيذ                                                 | لا تغيير         |

**ما يجعل هذا مضمونًا في قاعدة البيانات، لا في الذاكرة:**

- سطر سجل العمليات والدفعة يُكتبان **في المعاملة نفسها**، فإما يلتزمان معًا أو لا يلتزم أي منهما.
- قيد `UNIQUE (tenant_id, recorded_by_membership_id, idempotency_key)` على `expense_payments` حاجز ثانٍ: لو فات السجل لأي سبب، يفشل
  الإدراج الثاني، فيُقرأ السطر القائم ويُعاد.
- مفتاح القيد هو العضوية لا المستخدم، لأن الدفعة شأن الشركة الحالية. وسجل العمليات نفسه مقيّد بالمستخدم كما اعتُمد (24 ساعة).

### 3. حماية الجدول الجديد حين يصير الاشتراك للقراءة فقط

C15 (`004_…`) يضع سياسات `RESTRICTIVE` على `expenses` و`contracts` فقط، و**لا يشمل `expense_payments`**. المقترح ملف بوابة جديد
للجدول وحده (لا تعديل على `004` ولا `005` ولا `006`)، على نمط C16:

```sql
-- مسودة للمراجعة، لا تُشغَّل كما هي. تحتاج موافقتك وموافقة فريق الخلفية، ورقمًا جديدًا
CREATE POLICY commercial_select ON ambs_txn.expense_payments AS RESTRICTIVE FOR SELECT
  TO poc_txn_login, poc_fin_login USING (ambs_billing.ops_eligible(tenant_id, false));
CREATE POLICY commercial_insert ON ambs_txn.expense_payments AS RESTRICTIVE FOR INSERT
  TO poc_txn_login, poc_fin_login WITH CHECK (ambs_billing.ops_eligible(tenant_id, true));
-- لا سياسة UPDATE ولا DELETE ولا منح لهما: الدفعة لا تُعدَّل ولا تُحذف في أي حالة اشتراك
```

- **ثلاث طبقات:**
  1. دالة الدفع تفحص الأهلية أولًا وتعيد `403 subscription_read_only` (العقد).
  2. السياسة `RESTRICTIVE` على `INSERT` ترفض الإدراج في قاعدة البيانات، حتى لو تخطّى الكود الفحص الأول.
  3. سياسة `expenses` في C15 القائمة ترفض تحديث `paid_amount` على صف المصروف.
- **تحوّل الاشتراك أثناء الدفعة:** السياسة تُقيَّم عند `INSERT` نفسه. فإن صار الاشتراك للقراءة فقط قبل تلك اللحظة، يُرفض الإدراج
  وتتراجع المعاملة كلها، ولا يبقى نصف دفعة.
- **المعلَّق:** قبول هذه السياسات تشغيليًا يحتاج تجربة مثل C17، بالمنهج نفسه (تراجع، بلا قبول منتج). لم أشغّل شيئًا.

**في الخادم الوهمي (للتوثيق، لا بديل عن القاعدة):** `tests/s3-api.test.ts` يتحقق من ثلاث حالات:

- دفعتان متتاليتان من المحاسب والمالك: الثانية `overpayment`.
- إعادة الطلب بالمفتاح نفسه: دفعة واحدة والرد نفسه، والمفتاح نفسه بمبلغ آخر `422`.
- اشتراك منتهٍ: `403 subscription_read_only` ولا سطر جديد.

الخادم الوهمي يعمل طلبًا بعد طلب، فلا يثبت التزامن الحقيقي. ذلك يُثبت في الخلفية باختبار معاملتين متوازيتين.

## أين تبقى `paid_amount` و`paid_on` و`settlement_status`

| الخيار          | الوصف                                                                                                                                            | الخطر                                                                                                                                  |
| :-------------- | :----------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------- |
| **أ (أوصي به)** | تبقى أعمدة على `expenses` كما في الـERD، وتحدّثها دالة الدفع وحدها في المعاملة نفسها، مع `CHECK (paid_amount <= amount + coalesce(tax_amount,0))` | اختلاف بين العمود ومجموع الدفعات إن كتب أحد خارج الدالة. يُمنع بالصلاحيات (لا `UPDATE` مباشر على هذه الأعمدة)، ويُكشف باستعلام تحقق دوري |
| ب               | تُحذف من `expenses` وتُحسب في عرض (view) من الدفعات                                                                                                | أنظف، لكنه يغيّر الـERD ويؤثر في استعلامات التقارير القائمة في التصميم (`R4` في خطة الترحيل)                                            |

## الأثر على البيانات القائمة

- **الإنتاج:** لا بيانات، فلا أثر.
- **مختبر PoC:** جدول `expenses` فيه لا يحمل حقول الدفع أصلًا، والصفوف الستون الاصطناعية بلا دفع. الهجرة تضيف جدولًا فارغًا ولا تغيّر أي صف.
- **إن وُجدت صفوف فيها `paid_amount > 0` قبل الهجرة** (مثلًا من ترحيل Notion): تُنشأ لكل صف دفعة واحدة بمبلغ `paid_amount`
  وتاريخ `paid_on`، و`recorded_by_membership_id` = عضوية الترحيل، و`idempotency_key` = `migration:<expense id>`. ويُعلَّم أن تفاصيل
  الدفعات الجزئية السابقة غير معروفة. ولا يُفترض `paid` لما لم يُسجَّل دفعه (خطة الترحيل، السطر 98).
- **استعلام التحقق بعد الهجرة:** لكل مصروف، `paid_amount` = مجموع دفعاته، ولا مصروف مجموع دفعاته أكبر من إجماليه. أي صف يخالف
  يوقف الإطلاق.

## ما لا يقرره هذا المقترح (يحتاج قرارًا مستقلًا)

1. **بوابة الاشتراك على الجدول الجديد.** C15 (`004`) يغطي `expenses` و`contracts` فقط، وفحصه المسبق يعدّ الجدولين. الجدول الجديد لا تشمله
   تلقائيًا. إضافة سياسات له مثل C16 قرار لفريق الخلفية وللمالك. **هذا المقترح لا يمس C15 ولا C16.**
2. **سياسات النطاق (RLS)** للجدول الجديد على غرار `15_finance_child_scope.sql`: القراءة والكتابة عبر صلاحية المصروف الأب ونطاق مشروعه.
3. **الأدوار والصلاحيات:** من يُدرج في الجدول (دالة الدفع وحدها بصلاحية `expense.pay`)، ولا `UPDATE` أو `DELETE` لأحد.
4. **رقم الهجرة وتحديث أساس الفحص (baseline)** يُعرضان على المالك قبل التشغيل، كما تقضي قواعد المشروع.
